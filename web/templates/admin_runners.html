Deploy a worker

Docker (any host with docker):
docker run -d \ --name harness-worker \ --restart unless-stopped \ -e HARNESS_URL=https://your-harness.example.com \ -e HARNESS_API_KEY=hth_... \ -e HARNESS_WORKER_NAME=eu-worker-1 \ -e HARNESS_WORKER_TAGS=eu,media \ ghcr.io/croogmandoo/testharness:latest \ python -m worker.worker

Native Linux (Ubuntu 22.04 / 24.04):
curl -fsSL https://raw.githubusercontent.com/croogmandoo/testharness/master/scripts/install-worker-on-ubuntu.sh | sudo HARNESS_URL=https://your-harness.example.com HARNESS_API_KEY=hth_... HARNESS_WORKER_NAME=eu-worker-1 bash

How dispatch works

When a scheduled run fires or someone clicks Run on the dashboard, the central harness checks the app's run_on: field. If set, the run is queued instead of executed locally; the next polling worker that matches the name or tag claims it. Workers run the test, submit results back, and the central harness fires alerts + webhooks exactly as if the test had run in-process.

Workers are a trust boundary — they receive fully-resolved app definitions with plaintext secrets. Only deploy workers in segments at least as trusted as the secrets they handle.
